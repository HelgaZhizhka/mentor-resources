# Оценка Mentor Resources и направления развития

Дата: 9 сентября 2026. Независимая инженерная и педагогическая оценка; не официальная позиция EPAM или RS School.

## Вывод

Продолжать стоит как ограниченный пилот помощника ментора. Сильная основа проекта — накопленные ситуации из ревью, объяснения и связь замечаний с учебными материалами. Слабое место — превращение этого материала в универсальный норматив и автоматическую оценку без достаточно проверенной системы применимости правил.

Предлагаемое обещание продукта: «Помочь ментору подготовить доказательное ревью конкретного задания и выбрать следующие учебные шаги студента».

Экономия времени и улучшение обучения пока являются гипотезами. В истории есть полезные ручные проверки на студенческих проектах, но в отслеживаемых файлах не найден воспроизводимый набор эталонных ревью с измерением точности, шума и времени ментора.

Связанные внешние учебники, видео и стартовые репозитории не являются полностью проаудированной частью этого обзора.

Это качественная экспертная оценка, а не измеренная шкала зрелости.

## Подтверждённые проблемы

### 1. Образцы «хорошего» кода не всегда безопасны или корректны

- `clean-code/Clean-Code-Fundamental-Part1.md:1216`: `item: unknown`, затем `item.price` без narrowing. Извлечённый пример выдаёт TS18046 на двух обращениях.
- `clean-code/Clean-Code-Fundamental-Part4.md:98`: generic constraint `(...args: unknown[]) => unknown` не принимает показанный callback `(query: string) => void` в strict function checking. Извлечённый пример выдаёт TS2345. Для проверки объявлена только внешняя функция `fetchSearchResults`, тело примера сохранено.
- `clean-code/TypeScript.md:242`: аннотация `Promise<User>` вокруг `res.json()` описана как обеспечение безопасности. Она не проверяет ответ API. В §4.1 того же документа правильно объясняется отсутствие runtime-валидации у утверждений типов.
- `clean-code/TypeScript.md:144`: положительный пример заменяет `any` на `unknown`, но затем приводит каждый элемент массива через `as`, не проверяя его форму. Вход `[null]` всё ещё приводит к ошибке доступа к свойству.
- `clean-code/React.md:352`: comparator `memo` сравнивает только `user.id`, хотя карточка выше выводит `name` и `email`. При тех же id и новых имени/email comparator разрешает пропустить нужное обновление. Это вывод из кода и контракта React; отдельный браузерный тест не запускался.
- `clean-code/Clean-Code-Fundamental-Part3.md:627`: `void fetchUsers()` показан рядом с обработкой промисов. `void` не обрабатывает rejection; явное игнорирование результата следует отличать от обработки ошибки.

Риск выше обычной опечатки: эти тексты одновременно учат студента и служат обязательными источниками для агента. Ошибка может систематически переходить в рекомендации.

Первоисточники: [TypeScript — Everyday Types](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html), [React — memo](https://react.dev/reference/react/memo), [typescript-eslint — no-floating-promises](https://typescript-eslint.io/rules/no-floating-promises/).

### 2. Рекомендации, соглашения и требования задания смешаны

В материалах встречаются обязательные named exports, структура компонента через `index.tsx`, ограничение числа параметров, длины файлов и CSS-вложенности. Эти решения могут быть разумны в конкретной команде, но сами по себе не доказывают ошибку программы или незнание темы.

В чеклисте уже есть хорошая оговорка об отсутствии абсолютных запретов. Однако отдельные главы и конфиги сохраняют категоричные формулировки. Например, CSS-раздел одновременно рекомендует reduced-motion override с `!important` и содержит пункт «Нет !important». React-раздел допускает санитизированный HTML, конфиг запрещает `react/no-danger` без исключения.

Следует различать: нарушение явно заданного критерия; воспроизводимый дефект; обоснованный риск поддержки; соглашение команды; необязательное развитие. Нарушение соглашения не должно автоматически становиться блокером курса.

### 3. Scoring React-скилла противоречит собственному safe mode

`react-course-review/SKILL.md:143` запрещает обвинять студента за пропущенные проверки и предлагает снижать уверенность. В строке 244 пример рекомендует снижение 96 → 86 в том числе потому, что lint/build/test не проверялись.

Неизвестность о проверке не равна недостатку работы. Нужны отдельные поля: статус критерия, подтверждение, ограничение проверки, влияние на официальный rubric. Субъективную общую оценку 0–100 без rubric лучше убрать из первого пилота. Пометка «решение за ментором» полезна, но сама по себе не устраняет влияние необоснованного числа.

Дополнительно: шаблон отчёта говорит «Score is omitted» без контекста, а правила требуют Recommended Mentor Score и без контекста. Требование обязательно иметь хотя бы одну находку со ссылкой на React также конфликтует с допустимым результатом «замечаний нет».

### 4. Pocket Mentor предполагает лишнее о проекте

- `SKILL.md:145`: нет `package.json` → HTML/CSS. Это пропускает обычный JavaScript, подключённый через `<script>`.
- React без TypeScript попадает в Vanilla JS, а не в React.
- Prompt предлагает читать dependencies из bootstrap JSON, но bootstrap их не выдаёт.
- `SKILL.md:274`: чистый запуск ESLint трактуется как проверка целого фиксированного набора правил. Фактическая конфигурация студента может ни одного из этих правил не включать; warnings также не обязательно приводят к ненулевому exit code.
- Bootstrap выбирает первый найденный вложенный `package.json`. При нескольких заданиях или frontend/backend это может быть неправильная область проверки.
- Safe mode может выдавать `deps_installed: true`, хотя наличие зависимостей не проверялось. Эти поля нельзя считать подтверждением выполнения проверок.

### 5. JSON-контракт ломается на диагностике с кавычками

В `pocket-mentor/scripts/init.sh:134` сначала экранируются кавычки, затем обратные слеши. На fixture с `console.error('Error: "quoted"'); process.exit(1)` bootstrap возвращает текст, который не проходит `json.loads`.

В аналогичном React-bootstrap порядок другой, и тот же fixture выдаёт корректный JSON. Причина локализована; изменения в рамках этого аудита не вносились.

Штатный smoke ищет названия полей через grep и не разбирает JSON полноценным parser. Поэтому проходящий `./init.sh` не доказывает соблюдение контракта на ошибочных сценариях.

### 6. Regex-checkers требуют проверки человеком/моделью

Временные fixtures подтвердили:

- `import { User as Person } ...` помечается как type assertion;
- строка `"console.log is useful for debugging"` помечается как вызов console;
- реальный вызов в `scripts/main.js` пропускается, если нет `src/`.

Кроме того, список допустимых типов коммитов не содержит `init`, тогда как README нового CV явно приводит `init:` среди допустимых префиксов. Основание для проверки должно поступать из выбранных правил школы/задания.

Bash допустим как дешёвый сбор сигналов. Он не должен заменять AST, ESLint или чтение исходников там, где требуется точный семантический вывод.

### 7. Judge не подтверждает корректность находок

`review.mjs:354`: judge получает путь, строку и первые 200 символов замечания, без исходного diff и полного доказательства. Он может сравнивать темы, но не устанавливать, существует ли дефект в коде.

`review.mjs:416`: если judge корректно отклоняет все замечания, код возвращает все исходные замечания. Это воспроизведено выполнением неизменённой функции с mock-ответом `drop`: вход 1, возвращён 1. Сетевая модель и GitHub не вызывались.

Отсутствие новых замечаний должно быть нормальным успешным результатом. Нужно отдельно рассматривать сбой проверки и обоснованное решение «всё отбросить».

### 8. Автоматическое PR-ревью обещает больше своего контекста

Prompt в `review.mjs:125` предлагает находить отсутствующие требования по diff. Отсутствие реализации в diff не доказывает отсутствие в проекте, особенно при PR второй части лендинга в ветку первой части.

Action загружает только один файл требований; связанные общие правила, rubric, стартовый багрепорт могут оказаться за пределами контекста. Нужен явный перечень загруженных источников и запрет делать вывод о полном выполнении по неполному набору.

Проверка структуры ответа модели слабая: JSON parse не подтверждает форму объекта или существование строки в актуальном diff. При 422 все комментарии переносятся в общий текст вместо проверки их доказательств. История reviews запрашивается по 100 элементов без обхода последующих страниц. Повторные synchronize-запуски не привязаны к проверенному commit в payload публикации.

References загружаются крупными пакетами, включая все Fundamentals для Vanilla JS. Ограничение diff в символах не ограничивает полный размер prompt. Эти ограничения следует измерить до обещаний «работает из коробки» на больших заданиях.

## Предлагаемая модель продукта

### Один процесс проверки, разные учебные задачи

Не требуется немедленно переписывать два skill или строить платформу. Сначала выделить общий процесс: получить выбранное задание и область кода; собрать доказательства; проверить применимость; подготовить черновик; дать ментору выбрать следующие шаги.

Результат полезно разделить на:

1. Что подтверждено и что не проверено.
2. Дефекты/нарушения задания с доказательствами.
3. Две-три основные учебные темы.
4. Вопросы студенту и действия для проверки понимания.
5. Дополнительные улучшения для желающих.

### Вместо «жёстко/мягко» — глубина и объём поддержки

Единые официальные критерии для всех; различаются объём обратной связи, степень подсказки и дополнительные задания.

| Настройка | Начальная поддержка | Обычное ревью | Углублённый разбор |
|---|---|---|---|
| Фокус | Текущая тема, основные сценарии | Требования и важные дефекты | Дополнительно границы и компромиссы |
| Подача | Пример и пошаговый ориентир | Объяснение и вопрос | Контрпример, альтернативы, аргументация |
| Объём | Все блокеры плюс 2–3 темы | Приоритетные замечания | Дополнительный необязательный backlog |
| Официальные баллы | По одному rubric | По одному rubric | По одному rubric |

Не следует автоматически выводить способности/мотивацию человека из качества кода. Контекст задаёт ментор: что уже проходили, над чем сейчас работают, какой объём feedback нужен.

Пример учебного цикла: агент описывает сценарий гонки двух поисковых запросов → студент воспроизводит → объясняет причину → исправляет → проверяет другой порядок ответов. Готовый патч можно предложить после попытки или по запросу. Успех — способность перенести понимание на следующий случай.

### Каталог практик вместо ещё одной энциклопедии

Для каждой практики нужны: проблема, последствия, когда применять, когда не применять, минимальный корректный пример, способ проверить и источник. Полезны устойчивые идентификаторы правил и связь с этапами курса.

«Функция длиннее 30 строк» заменить вопросами о числе ответственностей и трудности изменения. «Не использовать push» ограничить контекстом чужих данных/React state; мутация приватного массива внутри стека сама по себе нормальна. «Не использовать as» заменить проверкой того, какое доказательство стоит за утверждением типа.

Примеры, предназначенные для копирования, держать исполняемыми и проверять. Псевдокод явно маркировать. Учебные правила и оценочные критерии должны иметь различный статус.

## План проверки жизнеспособности

Предлагаемый бюджет — 4–6 недель для одного автора; это ориентир, не обещание сроков.

1. Исправить критичные образцы, JSON-контракт и scoring-противоречия. Приостановить расширение числа инструментов и автоматическую выдачу оценок.
2. Выбрать одно конкретное задание: Landing Page Part 2. Если доступ к React-менторам существенно проще, использовать существующее React-задание, явно отделив пилот от поддержки нового курса.
3. С привлечёнными добровольно 3–5 менторами собрать 10–15 работ/фрагментов разного качества, включая корректные альтернативы, неполный diff и безопасные случаи, которые нельзя ругать.
4. Сначала получить независимое человеческое ревью, затем сравнить с черновиком агента. Разногласия фиксировать, а не объявлять мнение одного эксперта истиной.
5. Сравнить с обычным коротким запросом той же модели, с тем же заданием и кодом. Проверить, добавляет ли именно проект пользу.
6. Повторно проверить часть работ после исправлений; оценить, умеет ли студент объяснить и перенести принцип.

Измерять: долю корректных и полезных замечаний; ложные блокеры; пропущенные существенные дефекты; полное время ментора с подготовкой и редактированием; успешность запуска; повторное добровольное использование; понимание студентом.

Пример заранее согласованных критериев продолжения: не менее 80% замечаний принимаются без существенной правки; медианное время ментора уменьшается на 25% или больше; нет систематического навязывания чужих критериев; большинство пилотных менторов добровольно используют инструмент повторно. Это продуктовые пороги для обсуждения, не научно установленные нормы. На маленькой выборке сообщать абсолютные числа, не только проценты. Каждый ложный блокер разбирать отдельно.

Если польза не превосходит обычный AI-запрос либо редактура занимает столько же, сколько самостоятельное ревью, прекратить развитие автоматизации. Сохранить и улучшать справочник, короткие чеклисты и банк реальных разобранных случаев. Это самостоятельный полезный результат проекта.

## Приоритеты

**Сейчас:** точность материалов, границы правил, одно задание, измеримый пилот помощника ментора.

**После положительного пилота:** self-review студента по запросу, повторная проверка исправлений, новые профили заданий, проверенная переносимость между агентами.

**Отложить:** универсального оценщика всех стеков, сложную цепочку агентов, массовый автокомментатор каждого push, платформу с кабинетами и аналитику личности студента.

Материалы и ручной менторский инструмент заслуживают продолжения. Масштабная автоматизация заслуживает его только после доказанного преимущества на реальных проверках.
