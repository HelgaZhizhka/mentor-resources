# AI-ревьюверы для код-ревью студенческих проектов

## Зачем это нужно

Большая часть работы при ревью — **механическая и повторяющаяся**: проверить, что нет `any` и `as`, что коммиты следуют Conventional Commits, что нет `console.log`, что выполнены требования ТЗ. Эту часть можно автоматизировать — и оставить ментору время на то, что AI делать не умеет: работу **именно с этим студентом** в **именно этой точке его обучения**.

С другой стороны, **студенту** часто нужен feedback не после сдачи проекта (когда уже поздно учиться по ходу дела), а **во время разработки** — пока он ещё пишет код и может попробовать другой подход. Сейчас этот feedback он получает только от ментора, через несколько дней. Также в случае если студент не получает обратной связи от ментора , он может не получить обратного feedback от AI.

Два инструмента в репо [`HelgaZhizhka/mentor-resources`](https://github.com/HelgaZhizhka/mentor-resources) решают эти две разные задачи.

---

## Два инструмента, две роли

|                          | **Pocket Mentor**                                         | **Student Reviewer**                                          |
| ------------------------ | --------------------------------------------------------- | ------------------------------------------------------------- |
| **Формат**               | Claude Code skill                                         | GitHub Action                                                 |
| **Кто запускает**        | Ментор вручную перед оценкой                              | Автоматически на каждый push в PR                             |
| **Кто читает результат** | Ментор → курирует → решает что отправить студенту         | Студент напрямую в комментариях PR                            |
| **Что анализирует**      | Весь проект целиком — структура, фичи, баллы по ТЗ        | Только diff текущего PR — качество написанного кода           |
| **Роль**                 | Помощник ментору на финальной оценке                      | Обучающий feedback студенту во время разработки               |
| **Стеки**                | HTML/CSS, Vanilla JS, TypeScript, React+TS                | HTML/CSS, Vanilla JS, TypeScript, React+TS                    |
| **Angular**              | Не поддерживается                                         | Не поддерживается                                             |

Инструменты не заменяют друг друга — они работают на разных этапах: студент пишет код и получает быстрый feedback от action; ментор перед оценкой запускает pocket-mentor для полной проверки.

## Pocket Mentor — инструмент ментора

### Что делает

Ментор клонирует репозиторий студента и в Claude Code запускает команду `/pocket-mentor`. Skill:

1. **Определяет стек проекта** автоматически — HTML/CSS, Vanilla JS, TypeScript или React+TS — и подтягивает только релевантные части материалов из `clean-code/*`.
2. **Запускает технические проверки**: `lint`, `build`, `tsc`, плюс bash-чекеры на `any/as/!`, `console.log`, Conventional Commits, запрещённые файлы (`.env`, `node_modules`, `dist`).
3. **Опционально читает ТЗ** через флаг `--context` (локальный файл или ссылка на README задания на GitHub).
4. **Анализирует исходный код** с помощью Claude Sonnet 4.6, опирается на критерии задания и материалы курикулума.
5. **Пишет структурированный отчёт** `CODE_REVIEW_REPORT.md` с разделами: Stack / Strengths / 🔴 Critical / 🟡 Recommendations / 🔵 Notes / Score (если был `--context`) / Summary / Manual checks.

### Каждая находка в едином формате

```
🔴 **Critical**: [Краткое название проблемы]

**What:** что именно не так в коде
**Why:** почему это создаёт проблему
**How to fix:** конкретное действие
📖 Reference: ссылка на clean-code/<файл>
```

Это не "ты нарушил правило X", а **объяснение концепции**. Ментор может пересылать комментарии студенту почти без редактирования, или адаптировать под себя.

### Три режима вывода

- **По умолчанию** — только локальный файл `CODE_REVIEW_REPORT.md`. Ментор читает, редактирует, сам решает что отправить студенту. Безопасный default.
- **`--output inline`** — публикует отфильтрованные комментарии прямо в PR от имени ментора. Перед публикацией показывает черновик и ждёт подтверждения. Лимит: все 🔴 без ограничений + максимум 5 🟡/🔵 (чтобы не перегрузить студента).
- **`--output issues`** — создаёт GitHub Issues только по 🔴 critical находкам. Удобно когда хочется явных tracked work items.

### Что даёт ментору

- **Экономия времени** — механический прогон делает skill, ментор остаётся для педагогики.
- **Стабильное качество** — модель залочена на Sonnet 4.6 (после сравнительного теста на 5 моделях), не зависит от усталости ментора.
- **Опирается на курикулум** — каждая находка ссылается на конкретный раздел `clean-code/*`, никаких выдуманных правил.
- **Score по ТЗ** — если передан `--context` с описанием задания, skill считает баллы по критериям.
- **Approval gate** — никогда не постит автоматически. Все публикации с подтверждением ментора.

### Установка (одной командой)

```bash
npx skills@latest add HelgaZhizhka/mentor-resources -g -a claude-code --skill pocket-mentor
```

Требования: Claude Code, `gh` CLI (только для режимов `--output inline` и `--output issues`).

### Кому подходит

- Менторам с большой нагрузкой — 10+ PR в неделю.
- Менторам которые только начинают — skill как scaffolding, постепенно вытесняется собственной интуицией.
- Когда нужен Score по rubric и объективная база для разговора со студентом.

### Кому может быть лишним

- Senior-менторам с сильной интуицией, которые предпочитают полностью персональный подход.
- Маленьким группам где время на ревью не критично.
- Если ментор склонен использовать AI как stamp-of-truth, а не как первый набросок — лучше не использовать вообще.

## Student Reviewer — инструмент студента

### Что делает

Студент копирует один файл в свой репозиторий (`.github/workflows/student-review.yml`). После этого на **каждый push в PR** автоматически запускается GitHub Action, который:

1. **Получает diff PR** и определяет стек проекта.
2. **Читает описание PR**, находит ссылку на задание RS School, фетчит его README — теперь AI знает чему именно учится студент.
3. **Анализирует diff** с помощью AI, опираясь на материалы из `clean-code/*` и требования ТЗ.
4. **Прогоняет findings через judge-агент** — он отсекает дубли (если эта тема уже была в предыдущем ревью этого PR) и слабые находки.
5. **Постит inline-комментарии** прямо в PR с объяснением концепций.

### Каждый комментарий — обучающий, а не сухой

```
🟡 **Recommendation: Function type used — это эквивалент any для функций**

**What:** что ты, видимо, имел в виду
**The concept:** объяснение принципа на простом языке
**How to fix:** конкретное действие
📖 Reference: ссылка на clean-code/TypeScript.md
```

Это **тренажёр перед менторским ревью**. Студент учится сам ловить типичные ошибки — subscription leaks, Function-типы, использование `any`, нарушение SOLID — до того как их найдёт ментор.

### Что даёт студенту

- **Мгновенный feedback** на каждый push. Не нужно ждать ментора несколько дней.
- **Обучающие комментарии** — объясняет концепцию, ссылается на материалы курикулума.
- **Проверка по ТЗ** — фетчит README задания и проверяет ключевые требования.
- **Severity подсказывает приоритет** — 🔴 чинить срочно, 🟡 паттерн который стоит выучить, 🔵 для финального полишинга.
- **Бесплатно из коробки** — работает на GitHub Models (free tier). Если хочется лучшего качества — можно подключить свой Anthropic/OpenAI/Gemini ключ.
- **Один файл — и поехали** — никаких настроек, никаких API-ключей по умолчанию.

### Установка

```bash
mkdir -p .github/workflows
curl -o .github/workflows/student-review.yml \
  https://raw.githubusercontent.com/HelgaZhizhka/skills-store/master/templates/workflows/student-review.yml
```

### Что критично понять

Action — это **opt-in** инструмент. Студент сам решает подключать его или нет. Если для конкретного студента это давление и overwhelm — он может не подключать. Если он на той стадии когда feedback во время разработки полезен — он подключает.

### Кому подходит

- Студентам RS School на stage 2 — учатся архитектуре, TypeScript, паттернам.
- Тем кто хочет получать feedback во время разработки, а не только после.
- Тем кто готов работать с критикой и видеть в ней рост, а не приговор.

### Кому может быть неполезен

- Тем кто на самой ранней стадии и нуждается сначала просто "написать и увидеть что работает".
- Тем для кого 5+ замечаний на PR создают паралич, а не мотивацию.
- Для них есть альтернатива — пусть ментор использует pocket-mentor и сам решает что и как доносить.

## Что эти инструменты НЕ делают

Честно про границы:

1. **Не оценивают полноту проекта (action).** Student Reviewer видит только diff. Если в проекте отсутствует роутинг или README — он не заметит, потому что в diff их просто нет. Эта проверка — за ментором (pocket-mentor её делает).
2. **Не заменяют ментора.** Это инструменты для механической части ревью. Педагогическая часть — индивидуальный подход к студенту, тон сообщения, soft skills feedback, разговор про подход — это работа ментора.
3. **Не работают с Angular.** Текущие правила в `clean-code/*` ориентированы на TypeScript, React, Vanilla JS, HTML/CSS. Angular-проекты skill пропускает с явным предупреждением. (Для Angular есть отдельные подходы у других менторов.)
4. **Не идеальны.** AI иногда ошибается. Поэтому в pocket-mentor — approval gate, в action — judge-агент для фильтрации, и оба инструмента **прозрачны**: ментор и студент видят что было найдено и почему.

## Принципы

1. **Ментор в центре решений.** Pocket Mentor по умолчанию пишет в локальный файл, который ментор курирует. Никакого автоматического постинга в PR без подтверждения.
2. **Opt-in для студентов.** Action подключается студентом самостоятельно. Никто не навязывает feedback тому кто к нему не готов.
3. **Обучение, а не оценка.** Комментарии в формате "вот концепция", а не "ты нарушил правило". Цитирование курикулума, чтобы студент мог пойти и разобраться.
4. **Прозрачность.** Оба инструмента опираются на материалы `clean-code/*` в этом репозитории, а не на "мнение модели". Если правило неактуально — можно поправить в курикулуме, и оба инструмента подхватят.

## Как это вписать в RS School

### Для ментора

Pocket Mentor — это **дополнительный инструмент** для финальной оценки PR. Использовать его не обязательно. Но если ментор берёт его в работу, это позволяет:

- Сократить время на формальные проверки (lint/build/типы/коммиты).
- Получить структурированный отчёт с привязкой к учебным материалам.
- Иметь объективную базу для разговора со студентом.
- При желании — публиковать комментарии прямо в PR одной командой (с approval gate).

Менторам с активной нагрузкой имеет смысл попробовать. Менторам которые делают мало ревью — выбор индивидуальный.

### Для студента

Student Reviewer — это **опциональный self-review во время разработки**. Студент может:

- Подключить action в свой репозиторий одной командой и получать feedback на каждый push.
- Использовать его как тренажёр перед менторским ревью.
- Игнорировать конкретные комментарии или отключить action на любом этапе.

Action не влияет на итоговую оценку ментора. Это инструмент для собственного развития.

### Что предложить обновить в документации RS School

Старые упоминания автоматизации в документации RS School ссылаются на устаревший прототип (промпт + скрипт), который был в этом репозитории ранее и удалён. Сейчас актуальное состояние:

- Для ментора — `pocket-mentor` (Claude Code skill). Старые ссылки на промпты/скрипты можно заменить ссылкой на: [README.md](https://github.com/HelgaZhizhka/mentor-resources/blob/master/.claude/skills/pocket-mentor/README.md).
- Для студента — `student-reviewer` (GitHub Action). Раздел можно завести с ссылкой на: [README.md](https://github.com/HelgaZhizhka/mentor-resources/blob/master/.github/actions/student-reviewer/README.md).
- Общая точка входа с описанием — [главный README](https://github.com/HelgaZhizhka/mentor-resources).

Обновление не обязывает RS School рекомендовать эти инструменты — достаточно дать студентам и менторам знание что они существуют. Решение использовать остаётся за каждым.
