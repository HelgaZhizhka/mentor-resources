# Безопасный рефакторинг

Рефакторинг меняет устройство кода, сохраняя его наблюдаемое поведение. Исправление ошибки или изменение требований — отдельное изменение: сначала опишите новый контракт, затем проверяйте его. Удобно разделять эти шаги в diff, чтобы на ревью было видно, где изменилось поведение.

Материал дополняет [организацию кода](Clean-Code-Fundamental-Part2.md), [асинхронность](Clean-Code-Fundamental-Part3.md#22-asyncawait) и [тестируемость](Clean-Code-Fundamental-Part4.md).

## 1. Зафиксируйте контракт

Перед изменением определите:

- Допустимые входы, пустые значения и границы диапазона.
- Возвращаемое значение, включая `undefined`, `null` и результаты Promise.
- Ошибки: когда они возникают, кто их обрабатывает и получает ли их вызывающий код.
- Побочные эффекты: изменение аргументов, запись данных, отправка сообщений и их порядок.
- Для асинхронного кода — отмену, повторные вызовы и возможность устаревшего ответа.

Тесты существующего поведения помогают работать с незнакомым кодом. Если обнаружили дефект, не объявляйте его желаемым поведением: согласуйте ожидаемый результат и добавьте отдельный тест на исправление.

## 2. Меняйте небольшими шагами

1. Запустите относящиеся к коду проверки до изменения. Если они уже падают, выясните причину.
2. Добавьте недостающую проверку контракта, которую может нарушить планируемое преобразование.
3. Сделайте одно понятное изменение: переименование, выделение функции или замену представления данных.
4. Повторите проверки и просмотрите diff. Убедитесь, что не изменили обработку ошибок и побочные эффекты незаметно для себя.
5. Продолжайте, если структура стала понятнее. Выделенная функция или класс не являются улучшением сами по себе.

Число вызовов внутри функции не определяет её ответственность. Координатор может выполнять несколько шагов одной задачи. Выделяйте отдельную функцию, когда у неё есть понятный смысл, подходящий уровень абстракции или независимая причина изменения.

## 3. Пример: словарь вместо switch

Для произвольной строки проверьте не только известные значения, но и ключи прототипа обычного объекта. Вариант с `Map` сохраняет fallback для всех неизвестных ключей.

```typescript
const sounds = new Map<string, string>([
  ['dog', 'woof'],
  ['cat', 'meow'],
]);

export const getAnimalSound = (animal: string): string => sounds.get(animal) ?? 'unknown';
```

Пример тестов для Vitest. Поместите функцию в `sounds.ts`, а тест — в `sounds.test.ts` в проекте с настроенными TypeScript и Vitest.

```typescript
import { describe, expect, it } from 'vitest';
import { getAnimalSound } from './sounds';

describe('getAnimalSound', () => {
  it.each([
    ['dog', 'woof'],
    ['cat', 'meow'],
    ['fox', 'unknown'],
    ['', 'unknown'],
    ['toString', 'unknown'],
    ['constructor', 'unknown'],
    ['__proto__', 'unknown'],
  ])('для %s возвращает %s', (input, expected) => {
    expect(getAnimalSound(input)).toBe(expected);
  });
});
```

Эти проверки обнаруживают реальную потерю поведения при замене `switch` на обычный объект с доступом `dictionary[key]`. Они не требуют конкретной внутренней реализации.

## 4. Пример: Promise-цепочка и async/await

Следующие функции имеют один контракт: вернуть число, а при ошибке `save` — результат `recover`. Если сам `recover` завершается ошибкой, её получает вызывающий код.

```typescript
type Save = () => Promise<number>;
type Recover = (error: unknown) => number | Promise<number>;

export const before = (save: Save, recover: Recover): Promise<number> =>
  Promise.resolve().then(() => save()).catch(recover);

export const after = async (save: Save, recover: Recover): Promise<number> => {
  try {
    return await save();
  } catch (error: unknown) {
    return recover(error);
  }
};
```

`return await` здесь нужен, чтобы локальный `catch` получил отклонение Promise от `save`. Один `await save()` потеряет возвращаемое значение, а `return save()` внутри `try` не передаст асинхронное отклонение этому `catch`. Начальная `Promise.resolve().then(...)` также превращает синхронный throw из `save` в отклонение Promise.

Положите функции в `processing.ts`, а тесты — в `processing.test.ts`:

```typescript
import { describe, expect, it } from 'vitest';
import { before, after } from './processing';

for (const process of [before, after]) {
  describe(process.name, () => {
    it('возвращает результат сохранения', async () => {
      expect(await process(async () => 42, () => -1)).toBe(42);
    });

    it('ожидает и возвращает результат восстановления', async () => {
      const failure = new Error('storage unavailable');
      let receivedError: unknown;
      const result = await process(
        async () => { throw failure; },
        async (error) => { receivedError = error; return 99; },
      );
      expect(receivedError).toBe(failure);
      expect(result).toBe(99);
    });

    it('передаёт ошибку восстановления вызывающему коду', async () => {
      const failure = new Error('recovery failed');
      await expect(process(
        async () => { throw new Error('save failed'); },
        async () => { throw failure; },
      )).rejects.toBe(failure);
    });
  });
}
```

Во втором тесте два assertions проверяют один сценарий восстановления. «Один тест — одна концепция» не означает «ровно один expect». Эти функции сохраняют описанные результаты и ошибки; если для вызывающего кода важен порядок микрозадач, проверьте его отдельно.

## 5. FIRST и границы тестирования

| Принцип | Как применить |
| --- | --- |
| Fast — быстрые | Unit-тесты выполняются быстро; обращения к сети выделены в подходящий слой проверок. |
| Independent — независимые | Тесты не требуют определённого порядка запуска и очищают своё состояние. |
| Repeatable — повторяемые | Время, случайность и внешние данные контролируются. Для возраста передавайте дату явно. |
| Self-validating — самопроверяющиеся | Результат определяется assertions, а не ручным чтением логов. |
| Timely — своевременные | Пишите проверки вместе с поведением, желательно до реализации, и до рискованного преобразования. |

Моки полезны для проверки собственной логики в изоляции, но не доказывают, что реальное API понимает запрос. Дополняйте их проверками границ:

- **Интеграционные тесты:** адаптер корректно сериализует запрос, читает ответ и преобразует HTTP-ошибки.
- **Контрактные тесты:** согласованная форма данных и ошибок поддерживается поставщиком и потребителем.
- **Learning tests:** небольшой исполняемый пример проверяет важное для приложения поведение сторонней библиотеки. Он помогает изучить зависимость и заметить изменение при обновлении.

Для сетевых сценариев используйте контролируемый сервер или предусмотренную тестовую среду. Unit-тесты не должны зависеть от доступности production-сервиса. Проверяйте успешный ответ, HTTP-ошибку, неверный JSON, неверную структуру, отмену и устаревший ответ там, где эти состояния возможны.

## 6. Самопроверка перед ревью

- Сохранились ли возвращаемые значения, ошибки и порядок значимых побочных эффектов?
- Проверены ли границы: пустой ввод, неизвестный ключ, день до и после границы даты?
- Дожидаются ли тесты асинхронной работы и обнаруживают ли необработанное отклонение?
- Отделено ли изменение требований от преобразования структуры?
- Стало ли проще объяснить задачу функции, а не только короче её тело?

Основа: Robert C. Martin, *Clean Code* (2008), главы 3, 8, 9, 14–16: одна задача на уровень абстракции, тесты границ, FIRST и небольшие проверяемые шаги. Рекомендации адаптированы к TypeScript; соглашения проекта и контракты платформы следует учитывать отдельно. Дополнительно: [Martin Fowler — Definition of Refactoring](https://martinfowler.com/bliki/DefinitionOfRefactoring.html).
